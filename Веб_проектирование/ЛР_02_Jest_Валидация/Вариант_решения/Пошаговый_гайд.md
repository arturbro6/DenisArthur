# Пишем проверки до сверки с готовым файлом

## 1. Подготовьте отдельный Node-проект

Скопируйте пример в рабочую папку, выполните `npm install`. Пример использует Jest 30 и CommonJS. Проверьте версии командой `npm ls --depth=0`, сохраните package-lock. Не копируйте node_modules в репозиторий.

## 2. Составьте таблицу сценариев

Для email: обычный адрес, отсутствие @, отсутствие точки, пробел, неверный тип. Для пароля: длины 7 и 8, нет буквы, нет цифры, неверный тип. Для возраста: 13,14,120,121,дробь,строка. Ожидания выводите из условий, не из текущей реализации. Для экспериментальной группы эта таблица должна быть составлена до обращения к ассистенту.

## 3. Начните с возраста

Напишите заглушку isValidAge, возвращающую false. Добавьте тест на 14 — он должен упасть. Реализуйте проверку целого числа и две включительные границы. Проверьте, что '18' не преобразуется в число автоматически.

## 4. Разберите пароль по трём правилам

Сначала проверка типа. Затем минимальная длина. Затем наличие буквы и цифры. Не добавляйте требование спецсимвола или заглавной буквы: этого нет в спецификации. На каждом шаге придумайте пароль, который проходит предыдущие проверки, но не проходит новую.

## 5. Проверьте email

До применения регулярного выражения проверьте строковый тип. Прочитайте шаблон по частям из теории. Самостоятельно напишите адрес с двумя @ и адрес с пробелом. Обоснуйте, почему они отвергаются. Нельзя обещать проверку доставки письма простым regex.

## 6. Запустите Jest

`npm test` — все проверки. `npm run test:cov` — отчёт покрытия. Откройте coverage/lcov-report/index.html и найдите именно ветви validators.js. Процент покрытия не доказывает правильность: тест без содержательного ожидания может исполнять строки, но не находить ошибки.

## 7. Проверьте силу набора

Временно замените age>=14 на age>14. Должен упасть тест нижней границы. Временно уберите проверку цифры пароля. Должен упасть случай «только буквы». Верните исправную реализацию. Не делайте из этих учебных мутаций вымышленные ошибки ассистента.

## 8. Дополнительный validateUser

Он собирает ошибки в фиксированном порядке: email, пароль, возраст. Приложенный вариант безопасно обрабатывает null и отсутствующие поля. В тестах сравнивайте весь объект через toEqual. Объясните errors.length===0.

## 9. Экспериментальная часть

После собственной таблицы запросите тесты у выбранного ассистента, сверяйте каждое ожидание со спецификацией. Замечание «нужен спецсимвол» отклоняется, если оно не следует из задания; подтверждённая ошибка проверяется конкретным входом и регрессионным тестом. В docs/PROMPTS.md находится пустой шаблон для фактических запросов и решений. Если требуемые два недостатка ещё не обнаружены, продолжайте анализ и зафиксируйте реальный результат; не придумывайте наблюдения.

## Самостоятельный шаг

Напишите по одному новому тесту на каждый валидатор. Затем найдите пример, который проходит toBeTruthy, но не toBe(true), и объясните, зачем нужна строгая проверка. Перед сдачей покажите вывод своих npm test и coverage, а не пример вывода из методички.

Типичные ошибки: ESM смешан с CommonJS; чтение length у null; автоматическое преобразование возраста из строки; ожидания взяты из ошибочной функции; неправильная граница 120; добавленные требования, которых не было в задании.
