# Как придумать тест, а не просто повторить пример

Тест состоит из входа, ожидаемого поведения и объяснения, какую ошибку он найдёт. Сначала изучают спецификацию, затем выбирают вход. Если ожидание вычислить тем же алгоритмом с той же ошибкой, тест может оказаться бесполезным.

| Ситуация | Что обнаруживает |
|---|---|
| Один элемент `[3]`, сумма 6 | Повторное использование одной позиции |
| Два одинаковых `[3,3]` | Ошибочное удаление дубликатов |
| Отрицательные числа | Неверное предположение «числа положительные» |
| Пара в конце | Преждевременный `return None` |
| Несколько пар | Слишком жёсткое ожидание единственной пары |
| Пустой список | Ошибки обращения по индексу |

`class TestAdd(unittest.TestCase)` объединяет проверки. Это наследование готовых методов проверок, не обязательно глубокое знание ООП. `self` — текущий объект теста. Методы с именами `test_...` обнаруживаются автоматически. `assertIsNone` проверяет именно отсутствие результата; `assertEqual` — равенство значений; `assertNotEqual` — различие индексов.

Пример необоснованного теста: ожидать исключение на строковом `target`, если контракт говорит только о целых числах и ничего не обещает для других типов. Это новая спецификация, а не обязательный тест.

[Документация unittest](https://docs.python.org/3/library/unittest.html).
